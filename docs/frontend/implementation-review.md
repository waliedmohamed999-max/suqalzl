## 2. مبادئ معمارية الواجهة (تُطبّق على كل الشاشات)

### 2.1 Server أولاً، وجزر Client صغيرة
- كل صفحة **Server Component**. الـ `'use client'` على مستوى الورقة فقط (المكون الصغير) حسب `tokens.md` 12.4.
- الجلب يتم في الصفحة (RSC) من `features/<feature>/queries.ts`، وهي ترجع **DTO** وليس كائن Prisma. المكونات Client تستقبل props من DTO فقط.
- **قاعدة سرية إلزامية:** أي prop يُمرر لمكون Client يُسلسل كاملاً في الـ RSC payload ويصل للمتصفح. لذلك ممنوع تمرير كائن Prisma أو أي كائن فيه حقول غير مطلوبة لمكون Client. الضمانات:
  - `import 'server-only'` في كل `queries.ts` و `service.ts`.
  - تفعيل `experimental.taint` في Next.js و `experimental_taintUniqueValue` على `floorPrice` و `autoAcceptPrice` عند قراءتها في `negotiation/service.ts`، فيفشل الـ render لو وصلت لمكون Client بالخطأ.
  - اختبار Playwright يفحص HTML والـ RSC payload (`self.__next_f`) لكل صفحات العميل والتاجر بحثاً عن المفاتيح `floorPrice` و `autoAcceptPrice` و `noteRaw` (مكمّل لاختبار backend 5.6-6 الذي يفحص JSON).
- **الكتابة** عبر Server Actions (`features/<feature>/actions.ts`) تبدأ كلها بـ `requirePermission` (backend). الواجهة تستخدم `useActionState` و `useFormStatus` للحالات (submitting، error) وتمنع الإرسال المكرر.

### 2.2 التخزين المؤقت (Caching)
| نوع الصفحة | الاستراتيجية | ملاحظات |
|---|---|---|
| الرئيسية، المنتج، الباقة، صفحة التاجر، الصفحات الثابتة | ISR + `revalidateTag` عند تحديث المنتج/العرض/البانر | **لا قراءة لـ `cookies()` أو `headers()`** داخل الصفحة حتى تبقى static. أي جزء خاص بالمستخدم (المفضلة، عداد السلة، حصة الفصال) جزيرة Client تجلب بعد التحميل |
| التصنيف و `/products` و `/search` بفلاتر في الـ URL | render ديناميكي + كاش بيانات على مستوى الاستعلام (`unstable_cache` بمفتاح الفلاتر المطبّعة + tags) | تركيبات الفلاتر لا نهائية فلا ISR لها. الصفحة بدون فلاتر (`/c/[slug]`) تبقى ISR |
| `/souq` | shell بـ ISR قصير (مثلاً 60 ثانية) + Suspense streaming للأقسام + Realtime بعد الـ hydration | الأرقام الحية تتحدث من القناة، والـ shell لا يحتاج render لكل زائر |
| السلة، الدفع، الحساب، `/vendor`، `/admin`، الفصال | ديناميكي، `no-store`، `Cache-Control: private` | لا شيء خاص بمستخدم يدخل أي كاش مشترك |

**خطر (ملاحظة 8):** في أي استضافة ذاتية بأكثر من instance (Cloud Run أو غيره، حسب O6 في P7)، كاش ISR محلي لكل instance و `revalidateTag` لا ينتشر. المقترح لـ devops-engineer + backend-engineer: `cacheHandler` مخصص مشترك (Redis للـ tags + تخزين مشترك للصفحات)، أو عند الإطلاق instance واحد أو عدد صغير مع revalidate زمني قصير كحل مؤقت، مع العلم أن الحل المؤقت يعني أسعاراً قديمة لدقائق. **في التطوير (P1–P6) instance واحد، فالمشكلة لا تظهر محلياً**؛ لذلك أكتب الـ tags من البداية وأضيف اختبار staging بـ instanceين في P7. **السعر النهائي يُتحقق منه دائماً في السلة والـ checkout على السيرفر**، فالخطر على الثقة وليس على المال.

### 2.3 الصور
- `next/image` لكل الصور بالـ `sizes` في `tokens.md` 12.3 و `width`/`height` من الـ DTO دائماً (لمنع CLS).
- **المقترح (ملاحظة 9):** عند الرفع يولّد الـ backend (job خلف `JobScheduler`) نسخاً مشتقة AVIF و WebP بالعروض المعتمدة في `deviceSizes` و `imageSizes` وتُحفظ في الـ bucket العام، والواجهة تستخدم `loader` مخصصاً يحوّل `(src, width, quality)` إلى رابط النسخة المشتقة، فيعمل بنفس الشكل محلياً وعلى أي استضافة (ومعه CDN في P7). البديل: تحسين `next/image` داخل الحاوية مع `minimumCacheTTL` طويل وكاش CDN أمام `/_next/image`. القرار لـ backend-engineer + devops-engineer، والمراجعة لـ design-system-performance.
- صورة LCP واحدة بـ `priority` لكل صفحة (أول بانر، أول صورة في المعرض، أول بطاقة في التصنيف).

### 2.4 الحالة في الـ URL
- الفلاتر والترتيب والترقيم والتبويب النشط في `/souq` وصندوق التاجر و `?bargain=1` كلها في `searchParams`، عبر مكتبة `nuqs` (القسم 7) حتى تكون مكتوبة النوع ومشتركة بين Server و Client.
- **سلوك زر الرجوع:** فتح نافذة "اطلب سعرك" يضيف `?bargain=1` بـ `push`، فالرجوع يغلقها. تغيير الفلاتر في الديسكتوب `replace` حتى لا يمتلئ التاريخ.

### 2.5 الـ Realtime في المتصفح (خلف `RealtimeProvider`)
- **اتصال SSE واحد لكل تبويب** عبر `EventSource` الأصلي (صفر KB مكتبات)، على `/api/realtime/stream?topics=…`. السيرفر يتحقق من صلاحية كل topic من الجلسة (لا يقبل `vendorId` من العميل).
- **hook واحد** `useRealtime(topics, onEvent)` فوق مدير اتصال مشترك (multiplex)، فلا تفتح كل بطاقة اتصالاً.
- **إعادة الاتصال:** backoff أسي مع jitter (1، 2، 4، 8، حتى 30 ثانية)، و `Last-Event-ID` للاستكمال، وعند كل إعادة اتصال **جلب snapshot** كامل للعناصر الظاهرة (لا نعتمد على وصول كل الأحداث).
- **heartbeat** من السيرفر كل 25 ثانية يحمل `serverTime` (يصحح فرق الساعة للعدادات). لو لم يصل heartbeat خلال 45 ثانية يُعتبر الاتصال منقطعاً.
- **بانر "انقطع التحديث المباشر"** يظهر بعد فشل محاولتين متتاليتين (حوالي 3 ثوانٍ)، وليس عند أول انقطاع لحظي (سؤال للمصمم في 4.2).
- **التبويب المخفي:** يُغلق الاتصال بعد 60 ثانية من `document.hidden`، ويُعاد فتحه مع snapshot عند الرجوع. هذا يخفف الاتصالات المفتوحة على السيرفر أياً كانت الاستضافة.
- **بديل polling:** لو فشل SSE ثلاث مرات (proxy يخزّن الاستجابة مثلاً) ننتقل لـ polling كل 30 ثانية على نفس الـ snapshot endpoint.
- **قاعدة السرية:** القنوات الخاصة (`pr:{n}:customer`، `pr:{n}:vendor:{id}`، `vendor:{id}:inbox`) تحمل `{type, id, version}` فقط، والواجهة تجلب DTO من API محمي. القناة العامة `souq` يمكنها حمل بيانات عامة أصلاً (الكمية المتبقية، الحالة، `endsAt`) لتقليل الطلبات (اقتراح لـ backend-engineer في 5.6).

### 2.6 العدادات
- **ساعة واحدة مشتركة** للصفحة (`useSyncExternalStore`، tick كل ثانية، تتوقف مع `document.hidden`) حسب `tokens.md` 11.3.
- الوقت المتبقي = `endsAt − (Date.now() + serverOffset)`، و `serverOffset` من `serverTime` في الـ DTO ثم من الـ heartbeat.
- عند الصفر: `onExpire` مرة واحدة، والبطاقة تنتقل لحالة "انتهى" فوراً، ثم تتأكد الحالة من السيرفر (لا نثق بالساعة المحلية للشراء).

### 2.7 i18n و RTL
- `next-intl` بمسار `[locale]`، و `dir` من اللغة، والرسائل مقسمة بـ namespaces، ولا تُمرر للـ Client إلا رسائل الجزيرة نفسها (ميزانية `tokens.md` 12.4).
- الجمع العربي (عرض/عرضان/عروض، قطعة/قطعتان/قطع، تاجر/تاجران/تجار) عبر ICU plural في `messages/ar.json`، والنصوص النهائية لـ arabic-content-seo.
- الأرقام لاتينية في كل مكان، والتواريخ ميلادية (`ar-SA-u-ca-gregory-nu-latn`)، والمدخلات الرقمية تقبل ٠–٩ و ۰–۹ وتحوّلها (`toLatinDigits`).
- قواعد CI في `tokens.md` 10 (grep للخصائص الفيزيائية، والأوزان، والـ hex) تُفعّل من أول PR.
- **رمز الريال (D25، `tokens.md` 1.1 §8.4):** مكوّن `Price` وحده يولّد الـ markup الملزم (الرقم في `<bdi dir="ltr">` ثم U+00A0 ثم `span.riyal` بـ `role="img"` و `aria-label`)، والرمز يسار الرقم بصرياً في اللغتين. وجه `Souq Riyal Sign` (حوالي 1KB، `unicode-range: U+20C1`، `font-display: block`، preload) أول عنصر في `--font-sans`. **ممنوع** كتابة "ر.س" أو U+20C1 يدوياً في أي مكون، وقاعدة grep في CI تمنع ذلك خارج `Price` و `lib/format/money.ts`. القنوات التي لا نتحكم في خطها (SMS، الإيميل النصي، CSV) تستخدم "ر.س"/`SAR` نصاً حسب `tokens.md` 8.4.6. **حاجب جزئي:** ملف الرمز الرسمي من ساما لم يُنزّل بعد؛ حتى يصل يعرض `Price` "ر.س" نصاً خلف نفس الواجهة، فالتبديل لا يمس أي شاشة.

### 3.2 الدخول و OTP — `/login` (لوحات Login-mobile، OTP-mobile، Login-desktop، Login-staff-desktop، Login-states)

- **المكونات:** `Input variant="phone"` (بادئة +966، `dir="ltr"`، `inputMode="tel"`)، `Button lg`، `InputOTP` (مكوّن shadcn فوق `input-otp`)، `InlineBanner`، `ErrorState`، `Checkbox` (تذكرني).
- **النوع:** الصفحة 🟢، النموذجان 🔵 (react-hook-form + Zod + Server Actions).
- **البيانات:** `requestOtp(phone)` و `verifyOtp(phone, code)` و `staffLogin(email, password)` (القسم 5.3). لا شيء يُجلب قبل العرض.
- **الحالات المرسومة:** رقم غير صالح، جارٍ التحقق، رمز خاطئ مع المحاولات المتبقية، انتهاء الرمز، حد المحاولات (قفل ساعة)، فشل إرسال SMS. **ناقص:** وجهة ما بعد الدخول (`?next=`)، دمج سلة الزائر بعد الدخول، رسالة "عميل جديد" (هل نطلب الاسم بعد أول OTP؟).
- **ملاحظات تنفيذية:**
  - **أرقام `+9665` فقط** (D23): التحقق في الواجهة بـ regex بعد `toLatinDigits`، والنهائي على السيرفر.
  - **OTP 6 أرقام وليس 4** (D20، ملاحظة 1). أنفّذه بحقل واحد حقيقي (`autoComplete="one-time-code"`) بصناديق مرئية فوقه، وليس 4 أو 6 حقول منفصلة كما في اللوحة: الحقول المنفصلة تكسر التعبئة التلقائية من الرسالة في iOS، وقارئ الشاشة يقرأ "الرقم 1، الرقم 2…".
  - عداد "إعادة الإرسال بعد 00:42" يأتي من `resendAfterSec` في الرد، وليس ثابتاً في الواجهة.
  - رسالة "الرقم غير مسجل" ممنوعة (لا نكشف هل الرقم موجود). الدخول والتسجيل نفس المسار.
  - **دخول التجار والإدارة** مرسوم بـ "ثم رمز تحقق لجوالك المسجل" (2FA). SPEC يذكر بريداً وكلمة مرور فقط. لو اعتُمد الـ 2FA فهو نفس شاشة OTP بنص مختلف (سؤال لـ backend-engineer في 8).
- **مخاطر الأداء:** منخفضة. هذه صفحة خط الأساس للأداء في نهاية P1 (`tokens.md` 12.5).

### 3.3 الرئيسية — `/` (Home-mobile، Home-desktop، Home-states)

- **المكونات:** هيرو البانر (`<picture>` بمصدرين)، شبكة التصنيفات، شريط عروض الساعة داخل `data-surface="inverse"` (`DealCard rail` = `deal_card_mini`، `Countdown boxed` 🔵، `LiveBadge`)، `ProductCard grid` (+ `FavoriteButton` 🔵، زر "أضف إلى السلة" 🔵)، قسم الثقة، بطاقة "ابدأ البيع معنا"، الفوتر، `WhatsAppFab`.
- **النوع:** 🟢 بالكامل، كل `HomeSection` في `Suspense` مستقل (streaming)، والجزر: العداد، المفضلة، زر الإضافة، نقاط الشرائح.
- **البيانات:** `HomeDTO` (5.4.1): الأقسام مرتبة من `HomeSection`، البانرات، التصنيفات، أقرب عرض ساعة، عدد العروض المباشرة، منتجات الأقسام.
- **الحالات المرسومة:** تحميل، لا عروض ساعة (القسم يبقى بحالة "لا عروض الآن")، خطأ خادم، انقطاع الاتصال (نسخة محفوظة). **ملاحظة:** حالة "نسخة محفوظة · آخر تحديث قبل 12 د" تحتاج Service Worker للعمل بدون إنترنت، وهذا خارج SPEC. أقترح تنفيذها كبانر "أنت غير متصل" فقط (بدون cache offline) إلا لو قرر المالك PWA (4.2).
- **ملاحظات تنفيذية:**
  - الهيرو في التصميم **نص HTML + صورة جانبية** (5:4 ديسكتوب، 16:11 جوال)، بينما `tokens.md` 12.3 يعرّف البانر 16:9 جوال و 3:1 ديسكتوب بعرض كامل. لازم نسبة واحدة معتمدة وحقول البانر (`titleAr`، سطر فرعي، نص الزر، `imageMobile`، `imageDesktop`) (4.1-5).
  - "ادخل السوق: 128 عرض مباشر" رقم حي داخل صفحة ISR. أعرضه من الـ ISR (يتأخر حتى 60 ثانية) ولا أفتح اتصال Realtime في الرئيسية. العداد التنازلي يحسب من `endsAt` بدون اتصال.
  - شبكة التصنيفات مرسومة **بأيقونات خطية** لكل تصنيف، بينما `Category.imageUrl` في الـ schema صورة. القرار: أيقونة SVG ثابتة لكل تصنيف (14 أيقونة من designer) أم صورة يرفعها المالك؟ (4.1-6).
- **مخاطر الجوال:** الصفحة طويلة (4000px جوال). `content-visibility: auto` للأقسام تحت الطي، والصور lazy عدا الهيرو. ميزانية 150KB JS.

### 3.4 التصنيف والفلاتر — `/c/[slug]` (Category-mobile، Category-filters-mobile، Category-desktop، Category-states)

- **المكونات:** `Breadcrumbs` (+ JSON-LD)، `FilterChips` للتصنيفات الفرعية، شريط أدوات ثابت (تصفية بعدد، ترتيب، تبديل العرض)، شرائح الفلاتر المطبقة بزر إزالة، `ProductCard grid`، `Pagination` (ديسكتوب) و"عرض المزيد" بشريط تقدم (جوال)، `Sheet bottom` للفلاتر، `Checkbox` بعدد، `OptionChip`، `Swatch`، `Switch`، حقلا السعر + شريط مدى، `Select` للترتيب.
- **النوع:** الصفحة 🟢. الفلاتر 🔵 (تكتب في الـ URL عبر `nuqs`)، والنتائج تُعاد من السيرفر عند تغيّر الـ URL (`useTransition` لإبقاء النتائج القديمة ظاهرة أثناء التحميل بدل القفز).
- **البيانات:** `CategoryPageDTO` (5.4.2) بالمنتجات والـ facets بالأعداد، ونقطة `countProducts(filters)` خفيفة لزر "اعرض 23 منتج" داخل الـ Sheet.
- **الحالات المرسومة:** تحميل، لا نتائج للفلاتر (مع "إزالة كل الفلاتر" و"اطلب منتج بسعرك")، خطأ، مهلة تحميل المزيد. **ناقص:** تصنيف فارغ تماماً (بدون فلاتر)، ترقيم بعد آخر صفحة.
- **ملاحظات تنفيذية:**
  - **(ملاحظة 5، حاجبة للفلاتر)** فلاتر المقاس واللون والخامة تحتاج **خصائص موحدة لكل تصنيف** (مثلاً تصنيف البشوت: المقاس من قائمة ثابتة، اللون من قائمة ثابتة)، وكل `OptionValue` لأي تاجر يرتبط بقيمة موحدة. بدون هذا كل تاجر يكتب "أسود" و"اسود" و"Black"، فالفلتر لا يجمعها. المقترح لـ backend-engineer: `CategoryAttribute` و `AttributeValue` وربط `OptionValue.attributeValueId?`. حتى يُحسم: نطلق P2 بفلاتر **السعر والتاجر و"يقبل الفصال" و"عليه خصم" و"متوفر"** فقط.
  - **الجوال يطبّق عند "اعرض N منتج"، والديسكتوب فوراً** (README 4.4). في الجوال الحالة داخل الـ Sheet محلية، ونقطة العد تُستدعى بـ debounce 300ms.
  - **"عرض المزيد" في الجوال مقابل ترقيم في الديسكتوب:** أنفذ الاثنين على نفس `?page=`، و"عرض المزيد" يلحق الصفحة التالية في الـ Client ويحدّث الـ URL، وروابط الصفحات حقيقية للـ SEO.
  - شريط المدى للسعر مرسوم `aria-hidden` بجانب حقلين. أنفذ الحقلين كمصدر الحقيقة والشريط بـ Radix Slider (يدعم `dir="rtl"`) متزامن معهما.
- **مخاطر الأداء:** استعلامات الـ facets بالأعداد على Postgres مكلفة مع نمو المنتجات. ضمن حجم الإطلاق (حوالي 50 منتجاً + التجار) مقبولة. المراقبة عند p95 > 500ms ثم Meilisearch (devops 5.2).

### 3.5 صفحة المنتج — `/p/[slug]` (Product-mobile، Product-mobile-en، Product-desktop، Product-states)

- **المكونات:** `Breadcrumbs`، `ImageGallery pdp` 🔵 (سحب + صور مصغرة)، `IconButton` (مفضلة، مشاركة)، `RatingStars`، `VendorChip` (أو "يُباع من سوق الزل")، `Price lg with-compare`، `DiscountBadge`، سطر "شامل الضريبة"، `BnplSlot` 🔵، `VariantPicker` 🔵 (`OptionChip` + `Swatch` + `Select` للخامة)، رسالة المخزون `role="status"`، `QuantityStepper` 🔵، `Button primary lg`، بطاقة "عندك سعر في بالك؟" + `BargainButton`، معلومات الشحن، Accordion (الوصف، المواصفات، الشحن والاسترجاع، التقييمات)، "قد يعجبك أيضاً"، `StickyActionBar` (جوال)، `WhatsAppFab` مرتفع.
- **النوع:** 🟢 الصفحة + JSON-LD (Product، BreadcrumbList) + Open Graph. الجزر: المعرض، `VariantPicker` + السعر المتغير + المخزون + زر الإضافة (جزيرة واحدة "ProductPurchase" تشترك في حالة الـ variant)، المفضلة، `BnplSlot`، `PriceRequestSheet` (بـ `next/dynamic` عند `?bargain=1` أو الضغط).
- **البيانات:** `ProductDetailDTO` (5.4.3) فيه كل الـ variants بأسعارها وتوفرها، فلا طلب للسيرفر عند تغيير المقاس. والمخزون الدقيق لا يُرسل؛ يُرسل `lowStockLeft` فقط تحت الحد.
- **الحالات المرسومة:** تحميل، نفد الخيار (نبّهني + اطلب سعرك من تجار آخرين)، تغيّر المخزون أثناء الإضافة، 404. **ناقص:** تأكيد الإضافة للسلة (Toast أم Drawer سلة مصغرة؟)، المفضلة لزائر غير مسجل (الـ schema `Wishlist.userId` إلزامي)، منتج تاجر (كتلة "ينفّذه متجر …" بدل "يُباع من سوق الزل")، منتج سيوف (`BLADE`: بدون تقسيط).
- **ملاحظات تنفيذية:**
  - **نسبة صورة المعرض في الجوال:** README 4.2 يقول 4:5، و `tokens.md` 11.2 و 12.3 يقولان 1:1 جوال و 4:5 ديسكتوب، واللوحة مرسومة 4:5. أحتاج نسبة واحدة (4.1-4).
  - **صياغة "يُباع من":** مع O2 = A1 المنصة هي البائع قانونياً لكل الطلبات، و O8 يطلب "المتجر" أو "ينفّذه متجر …" وليس "البائع". "يُباع من سوق الزل" صحيحة لمنتجات المنصة، والنسخة الإنجليزية "Sold by Souq AlZal" كذلك، لكن منتجات التجار تحتاج صياغة مختلفة (لـ arabic-content-seo + legal-contracts).
  - **سطر التقسيط** مرسوم كنص منّا ("4 دفعات بقيمة 462.50 ر.س")، و `tokens.md` يسميه `BnplSlot` lazy (ويدجت طرف ثالث). أيهما؟ النص المحلي أخف وأسرع (لا سكربت)، لكن قد تفرض تابي وتمارا ويدجت رسمياً أو صياغة محددة. ويظهر فقط عند التأهيل وتحت السقف (T4). (سؤال لـ backend-engineer في 8.)
  - "يتنافس صاحب المنتج و12 تاجراً في البشوت" رقم يأتي من السيرفر (`estimatedRecipients`) مع حد 30 مستلماً (O9).
  - نسخة LTR (Product-mobile-en) تثبت الانعكاس بشكل صحيح. أعتمدها مرجعاً لاختبار الإنجليزي في Playwright (لقطة بصرية واحدة لكل لغة).
- **مخاطر الجوال:** المعرض هو الـ LCP: أول صورة server-rendered بـ `priority`، والسحب (Embla) يتحمّل بعد الـ hydration. ميزانية 170KB. `BnplSlot` بارتفاع محجوز.

### 3.6 نافذة "اطلب سعرك" — `/p/[slug]?bargain=1` (Bargain-mobile، Bargain-desktop، Bargain-states)

- **المكونات:** `Sheet bottom` (جوال، top 64px) / `Dialog` 720px بعمودين (من `md`)، ملخص المنتج والـ variant، `PriceRequestForm` (حقل السعر الكبير 24–26px، `dir="ltr"`)، اقتراحات −5/−10/−15/−20%، `QuantityStepper` (`Stepper`)، `Select` المدينة، الإجمالي المحسوب، "كيف يمشي طلبك"، سطر الحصة (O9)، `Callout secure`، `InputOTP` داخل النافذة.
- **النوع:** 🔵 بالكامل، محمّل بـ `next/dynamic`. السياق الخاص بالمستخدم (`BargainContextDTO`) يُجلب عند الفتح من route handler (`GET /api/negotiation/context?variantId=`) لأن الصفحة ISR.
- **البيانات:** `BargainContextDTO` و `createPriceRequest` (5.4.4). **لا `floorPrice` ولا `autoAcceptPrice` في أي منهما.**
- **الحالات المرسومة (7):** تحقق الجوال قبل الإرسال، سعر خارج النطاق، حد الطلبات المفتوحة، جارٍ الإرسال، خطأ شبكة، نجاح، قبول تلقائي. **ناقص:** منتج بخيارات ولم يختر العميل المقاس بعد، طلب مفتوح موجود على نفس المنتج (O9: طلب واحد لكل منتج) مع رابط له، الحساب الجديد بحد 2/3 (O9)، ميزة الفصال معلّقة للعميل (بعد 3 محاولات تواصل)، الحد اليومي (10) منفصلاً عن المفتوح (5).
- **ملاحظات تنفيذية:**
  - **(ملاحظة 2)** التأخير العشوائي 2–10 دقائق **معتمد** (D22)، فلا توجد لحظة "قُبل فوراً" في النافذة. **لن أنفّذ حالة "قبول تلقائي" المرسومة.** الحالة الصحيحة: نجاح عادي "وصل طلبك لـ N تاجراً"، ثم بعد دقائق يصل عرض مقبول من صاحب المنتج كأي عرض (إشعار + تحديث في صفحة الطلب + وسم "قبول تلقائي"). **رد الإرسال يجب أن يكون متطابقاً** سواء كان السعر فوق `autoAcceptPrice` أو تحت `floorPrice` (backend 5.6-3). المصمم يحذف الحالة من Bargain-states.
  - **التحقق من الجوال داخل النافذة:** زائر غير مسجل يضغط "اطلب سعرك" ← OTP داخل الـ Sheet ← الجلسة تُنشأ (Server Action تضع الكوكي) ← يُرسل الطلب بنفس المدخلات بدون مغادرة الصفحة. أحفظ مدخلات النموذج في الحالة المحلية أثناء الـ OTP، ودمج السلة يحدث في الخلفية.
  - **الحد الأدنى المعروض** "أقل سعر نقبله لطلبات هذا المنتج 925.00 ر.س" هو `minTargetPrice` العام (50% من سعر الـ variant حسب O9)، ومكتوب في حالة الخطأ أنه ليس حد التاجر. هذا صحيح. **اقتراح صياغة** لـ arabic-content-seo: "أقل سعر يُقبل في طلبات هذا المنتج" بدل "نقبله" (صيغة المتكلم توحي بأنه حد البائع).
  - الحقل مرسوم `inputmode="numeric"`، والـ handoff يقول `decimal`. هل يكتب العميل هللات؟ أقترح **ريالات صحيحة للعميل** (أبسط، والاقتراحات أصلاً بالريال)، وهللات مسموحة للتاجر. (سؤال لـ backend-engineer + designer.)
  - الاقتراحات السريعة تُحسب على السيرفر أو بحساب صحيح بالهللة (`Math.round` على Integer)، وتُقرّب للريال، ولا تنزل تحت `minTargetPrice`.
  - أقصى كمية = `min(المخزون المتاح، إعداد عام)` من الـ DTO.
- **مخاطر:** الـ Sheet طويل على الجوال (1260px)، والزر ثابت في الأسفل مع لوحة المفاتيح المفتوحة على iOS. أستخدم `visualViewport` لرفع الشريط وأختبر على iPhone SE.

### 3.7 السلة — `/cart` (Cart-mobile، Cart-states)

- **المكونات:** `ShipmentGroup` لكل تاجر (الاسم، المدة، رسوم الشحن)، `CartLine default | deal-locked | price-locked | unavailable` 🔵، `QuantityStepper locked`، `PriceLockBadge` 🔵، `InlineBanner`، `OrderSummary cart` (كوبون، المنتجات، الخصم، الشحن، الإجمالي، الضريبة المضمنة، سطر التقسيط)، `StickyActionBar` ("إتمام الطلب · المبلغ").
- **النوع:** الصفحة 🟢 (ديناميكية)، والسطور والملخص 🔵 (تعديل الكمية والحذف والكوبون عبر Server Actions مع `useOptimistic` للكمية فقط، والإجمالي دائماً من رد السيرفر).
- **البيانات:** `CartDTO` (5.4.5) يحسب كل شيء على السيرفر (الأسعار، الأقفال، الملاحظات `notices[]`). الواجهة لا تحسب أي مبلغ.
- **الحالات المرسومة:** تحميل، فارغة، فشل الدفع، انتهاء PriceLock، انتهاء قفل عرض الساعة، تغيّر المخزون. **ناقص:** كوبون غير صالح أو منتهٍ، تجاوز `perCustomerLimit`، حذف عنصر بسعر مقفول (هل يُلغى الـ PriceLock ويفك المخزون؟ تأكيد مطلوب)، تعليق التاجر (`SUSPENDED`) لعنصر في السلة، دمج سلة الزائر بعد الدخول.
- **ملاحظات تنفيذية:**
  - **نغمة عنصر الفصال:** اللوحة تستخدم info ("سعر فصال مقفول")، و README 3-9 و `tokens.md` 2.5 يقولان accent. أنفّذ accent (4.4).

### 3.9 السوق الحي — `/souq` (Souq-mobile، Souq-desktop، Souq-states)

- **المكونات:** هيرو داكن (`LiveBadge`، أرقام السوق، "اطلب منتج بسعرك"، "كيف يعمل الفصال؟")، `Tabs underline` بعدد لكل قسم (عروض الساعة/اليوم/الأسبوع/تصفية/باقات/طلبات مفتوحة)، `FilterChips` + `SortMenu`، زر "3 عروض جديدة · اعرضها" (`aria-live="polite"`)، `DealCard` بأشكاله: مميز داكن (`deal_card_feature`)، أفقي (`horizontal` = `row`)، عمودي (`vertical`، ديسكتوب)، صغير فاتح (`deal_light_mini`)، `Countdown`، `InlineTimer`، `StockMeter` (`StockBar`)، `RequestTicker`، بطاقة "ما لقيت اللي تبيه؟"، بطاقة الباقة، عمود جانبي 360px (ديسكتوب).

- **ملاحظات تنفيذية:**
  - **التخفيضات طول السنة (D16):** الوضع المرسوم هو الافتراضي. لكن الإعداد `souqDiscountsRequireLicense` قد يُفعّل لاحقاً بدون تعديل كود، وحينها خارج فترات الترخيص تعرض `/souq`: طلبات الفصال المفتوحة، "اطلب سعرك"، وصل حديثاً، والمنتجات القابلة للفصال **بدون سعر قبل/بعد**. أبني الصفحة بـ `mode` من السيرفر (`DEALS` | `NO_DISCOUNT`) من البداية حتى لا نعيد البناء. الوضع الثاني **ليس حاجباً**؛ يحتاج تصميماً قبل تفعيل الإعداد (أقل أولوية).
  - **"تاجر نشط الآن" (41)** يحتاج تتبع حضور (presence) غير موجود في الـ backend. المقترح: استبداله بـ "تاجر لديه عروض مباشرة" أو حذفه (designer + backend).
  - **عدد العروض الجديدة:** حدث `deal.created` لا يُحقن في القائمة؛ يزيد عداد الزر فقط، والضغط يجلب القسم من السيرفر ويحافظ على موضع التمرير والتركيز (README 3-4).
  - **تحديث "باقي X":** في مكانه + وميض `warning-subtle` 600ms (يُلغى مع reduced-motion). عند الوصول للصفر: البطاقة "نفدت الكمية" فوراً، والزر يُستبدل بـ "نبّهني بعروض مشابهة". **ما وظيفة "نبّهني"؟** لا يوجد نموذج اشتراك تنبيهات في الـ schema (backend + designer).
  - **الحدة الزمنية للعدادات غير موحدة** (ملاحظة 4.4-6): اللوحات تلوّن كل العدادات warning حتى 42 دقيقة، و `tokens.md` يقول warning تحت 10 دقائق و danger تحت 5.
  - **`StockMeter`:** اللوحة تعطي الشريط `role="progressbar"` بقيمة "المباع"، و `tokens.md` 11.3 يقول الشريط زخرفي `aria-hidden` والنص هو المعلومة. أنفّذ `tokens.md`.
  - "اشترِ الآن" يضيف للسلة ويذهب لها مباشرة؟ أم يضيف ويبقى؟ (designer).
  - تابات الأقسام: هل هي tabs حقيقية (لوحة واحدة ظاهرة) أم روابط قفز لأقسام في نفس الصفحة؟ اللوحة تعرض كل الأقسام تحت بعضها مع tablist، وهذا تعارض دلالي في ARIA. المقترح: روابط قفز sticky (`nav` + `aria-current`) وليس `role="tab"`، أو tabs حقيقية مع `?tab=` في الـ URL (designer).
- **مخاطر الأداء (الأعلى في المشروع):** صفحة 4200px جوال، 10+ عدادات، اتصال دائم. الضوابط: ساعة واحدة، اتصال SSE واحد يبدأ بعد الـ hydration في `requestIdleCallback`، تحديث العنصر المتأثر فقط، صور 116px بـ `sizes="120px"`، `content-visibility` للأقسام السفلية، ميزانية 180KB. **على السيرفر:** كل تبويب مفتوح = اتصال طويل مفتوح على السيرفر (حد الاتصالات لكل instance، ومهلة الطلب في الـ proxy، وتخصيص CPU في بعض الاستضافات؛ يُقاس عند اختيار الاستضافة في P7). إغلاق الاتصال في التبويب المخفي (2.5) يقلل هذا كثيراً. اختبار حمل في P6 (devops).

- **النوع:** الصفحة 🟢 (قائمة + تفاصيل في الديسكتوب)، القائمة 🔵 مشتركة في `vendor:{id}:inbox`، النموذج 🔵.
- **البيانات:** `VendorInboxItemDTO` و `VendorRequestDetailDTO` و `MatchingProductsDTO` و `previewOffer` و `submitVendorResponse` (5.4.11).
- **الحالات المرسومة:** تحميل، فارغ، مغلق لصالح تاجر آخر، انتهاء مهلة الرد، فلتر التواصل، فشل الإرسال. **ناقص:** حالات النموذج لكل خيار في الـ radiogroup (القبول: السعر مقفول على سعر العميل؛ الاعتذار: سبب اختياري؟)، لا منتج مطابق عند التاجر، المخزون أقل من الكمية المطلوبة، رد العميل بسعر مضاد (العرض السابق في الخيط)، آخر جولة للتاجر، ميزة الفصال معلّقة للتاجر.
- **ملاحظات تنفيذية:**
  - **(ملاحظة 4، حاجبة)** النموذج يختار **منتجاً** فقط، و `PriceOffer` يحتاج `variantId`، والكمية ≤ مخزون الـ variant. المقترح: اختيار المنتج ثم الـ variant (أو قائمة مسطحة "المنتج · المقاس · اللون · السعر · المخزون"). لصاحب المنتج على طلب `PRODUCT`: المنتج والـ variant مقفولان على طلب العميل (designer + backend).
  - **(ملاحظة 7)** "العمولة التقديرية (10%) −330.00" و"صافيك 3,005.00" تتعارض مع معادلة finance (العمولة على الصافي قبل الضريبة، وإضافة 15% للتاجر المسجل). **الواجهة لا تحسب**؛ `previewOffer` على السيرفر يرجع `{customerTotal, commissionEstimate, netEstimate, vatNote}` عند كل تغيير (debounce 400ms). والأرقام التوضيحية في اللوحة تُصحح (designer).
  - **الحد الأدنى في النموذج:** اللوحة تعرض قيمة الحد (1,600.00) للتاجر، و backend 5.6-2 يقول `PriceRequestVendorDTO` يحمل `belowYourFloor: boolean` فقط. قيمة الحد هي إعداد التاجر نفسه على منتجه، فعرضها له لا يسرّب شيئاً لغيره، لكنه يعني إرجاعها في DTO. المقترح: `previewOffer` يرجع `yourFloorPrice` فقط لـ variant يملكه تاجر الجلسة، وقائمة الصندوق تبقى `belowYourFloor` boolean (backend يقرر).
  - **وسم "أقل من حدك الأدنى" في القائمة** معنى له فقط لصاحب المنتج (طلب على منتجه). للتاجر المنافس الحد يُعرف فقط بعد اختيار منتجه المطابق، فيظهر في النموذج وليس في القائمة (backend + designer).
  - **الصف رابط أم زر؟** اللوحة تجعله `<a href>`، و `tokens.md` 11.3 يقول "الصف كله زر يفتح ResponsePanel، والتنقل بالأسهم". المقترح: **رابط** لـ `/vendor/requests/[number]` (يعمل الرجوع، ويُشارك، ويُفتح في تبويب)، وفي الديسكتوب parallel route يعرض التفاصيل بجانب القائمة. التنقل بالأسهم إضافة اختيارية (design-system-performance).
  - **الرد في الجوال كـ Sheet** طويل جداً (1640px) ومعرّض لفقدان المدخلات بالسحب للإغلاق. المقترح: صفحة كاملة `/vendor/requests/[number]` في الجوال بدل Sheet (designer).
  - الأقسام (جديد/بانتظار ردي/…) تُشتق على السيرفر (`bucket`) وليس في الواجهة.
  - **السرية:** لا يظهر للتاجر عدد المنافسين ولا أسعارهم ولا الفائز؛ حالة "أُغلق لصالح تاجر آخر" كافية.

### 4.2 الحالات الناقصة (ملخص للمصمم)
1. **Realtime:** متى يظهر بانر الانقطاع (المقترح بعد محاولتين ~3 ثوانٍ)، ومتى يختفي (بعد أول snapshot ناجح)، وهل يظهر "آخر تحديث قبل X" دائماً أم عند الانقطاع فقط.
2. **الفصال للعميل:** منتج بخيارات بلا اختيار، طلب قائم على نفس المنتج، حد الحساب الجديد (2/3)، الحد اليومي، ميزة الفصال معلّقة، تأكيد إلغاء الطلب، عرض `isAuto`، طلب مفتوح بلا "سعر أصلي"، تحويل `CONVERTED`.
3. **الفصال للتاجر:** حالات كل خيار في الـ radiogroup، لا منتج مطابق، مخزون أقل من المطلوب، آخر جولة، ميزة الفصال معلّقة.
4. **السلة والدفع:** كوبون غير صالح، `perCustomerLimit`، تاجر معلّق، انتظار التحقق من الدفع، نجاح الطلب، انتهاء حجز الـ 30 دقيقة، وسيلة دفع غير متاحة.
5. **المتجر:** تأكيد الإضافة للسلة، المفضلة للزائر، منتج تاجر في صفحة المنتج، منتج `BLADE`.
6. **اللوحات:** صلاحيات جزئية (`STAFF`، `VENDOR_STAFF`)، تاجر مرفوض، الجداول على الجوال.

## 5. عقد البيانات المبدئي (Frontend ← Backend)

> **حالة العقد:** مقترح من الواجهة. **العقد النهائي هو مخططات Zod في `features/<feature>/schema.ts`** يكتبها backend-engineer (backend 5.6-2)، والواجهة تستورد الأنواع منها (`z.infer`). أي حقل هنا غير موجود في الـ schema الحالي معلّم بـ `NEW`.
> **الأشكال هنا TypeScript وصفية للتوثيق فقط**، وليست كود تطبيق.

### 5.1 أنواع مشتركة وقواعد عامة
```ts
type Halalas = number;      // integer, always (D7). Never a float, never a formatted string.
type Bps = number;          // basis points: 1000 = 10%
type ISODate = string;      // UTC ISO 8601
type Id = string;           // opaque

interface ImageDTO { url: string; alt: string; width: number; height: number }  // width/height mandatory (CLS)

interface VendorRefPublic {
  kind: 'PLATFORM' | 'VENDOR';
  slug: string | null;            // null when anonymous (O8 option B)
  displayName: string | null;     // "المتجر" wording, never "البائع" (O8)
  ratingAvg: number | null;       // 0..5, one decimal          NEW (vendor-level aggregate)
  ratingCount: number | null;     //                            NEW
  badges: Array<'FAST_REPLY' | 'HIGH_ACCEPTANCE' | 'TRUSTED'>;  // NEW (derived)
  acceptanceRateBps: number | null;                             // NEW
}
```
**قواعد:**
1. **النصوص تأتي محلولة بلغة الطلب** (`name` وليس `nameAr`/`nameEn`) في كل DTO عام، لتقليل الحجم. النماذج التي تحرر اللغتين (لوحات) تستقبل الحقلين.
2. **كل DTO فيه عداد يحمل `serverTime: ISODate`** لتصحيح الساعة.
3. **لا مبالغ منسقة من السيرفر**؛ الواجهة تنسق عبر `lib/format/money.ts`.
4. **رسائل الخطأ:** Actions ترجع `{ ok: false, code: 'PRICE_BELOW_PUBLIC_MIN' | 'QUOTA_OPEN' | 'QUOTA_DAILY' | 'CONTACT_INFO' | 'STALE' | … , fieldErrors? }`، والواجهة تترجم الـ `code`. **لا رسالة نصية من السيرفر** ولا أي code يخص `floorPrice` أو `autoAcceptPrice` (لا يوجد code مثل `BELOW_FLOOR` للعميل).
5. **أي قائمة ترقيمها server-side:** `{ items, page, pageSize, total }` أو `{ items, nextCursor }`.

## 6. خطة بناء الواجهة

**افتراضات التقدير:** أيام عمل لمهندس واجهة واحد بخبرة في Next.js، شاملة الاختبارات المرتبطة (Vitest للمكونات والدوال، Playwright للمسارات، axe)، و DoD في SPEC 10. **لا تشمل** انتظار الـ backend أو التصميم. الأرقام تقديرية بنطاق.

**قاعدة "بدون بيانات وهمية" (CLAUDE.md 7):** الواجهة لا تُبنى على mocks داخل التطبيق. لذلك **ترتيب كل مرحلة: الـ backend يسلّم مخطط Zod للـ DTO + query/action على الـ seed، ثم الواجهة**. اقترح على الـ CEO اعتماد أن fixtures مولّدة من مخططات Zod مسموحة داخل الاختبارات والـ Storybook فقط (لا تدخل أي route في التطبيق) حتى نبدأ المكونات بالتوازي مع الـ backend (سؤال في 8).

> **بيئة التطوير (D12):** كل المراحل تُبنى وتُختبر على `docker compose` محلي (Postgres 16 + تخزين S3-compatible) من devops-engineer، و SSE من نفس تطبيق Next.js، والدفع sandbox (D14)، والشحن يدوي (D17). لا شيء في الواجهة مرتبط بمزود استضافة، فلا مهام واجهة في P7/P8 غير إصلاحات النشر واختبار الـ staging.
